Running iOS Simulators with AI coding agents

An agent that changes an iOS screen should see it running, not guess from the code. macbox officially supports AI coding agents (Claude Code and Codex) and T3 Code: it gives every agent checkout its own iOS Simulator on your Linux machine, the commands to build, tap, screenshot and record it, a 60 fps check, and a skill that tells the agent when to use them.

{{meta}}

In short

  • ./macbox agents install installs mac-sim, sim-fps, android-sim, and the simulators skill for Claude Code and Codex.
  • ./macbox t3 register and ./macbox t3 fix-hub put the simulators in T3 Code's Device panel, streamed live.
  • Each checkout gets its own simulator, so agents in parallel worktrees don't wait for each other.

What's supported

These integrations are part of macbox and maintained in its repository. "Supported" here means macbox's own support; macbox isn't affiliated with or endorsed by Anthropic, OpenAI or T3.

Install

With a working macbox VM, Xcode and the pool (iOS Simulator on Linux):

./macbox agents install

It links mac-sim, mac-sim-remote, sim-fps, android-sim, android-gpu-desktop, phone-build and macbox into ~/.local/bin; links the skills into ~/.claude/skills and ~/.agents/skills; writes the simulators section between <!-- macbox:simulators --> markers in ~/.claude/CLAUDE.md and ~/.codex/AGENTS.md (each backed up first); and enables the timer that shuts idle simulators down. ./macbox agents uninstall removes the links and the timer.

What an agent does with it

From the app's checkout:

mac-sim up                     # claim a simulator from the pool and boot it
mac-sim run                    # copy the checkout to the Mac, build, install, open; Metro on Linux
mac-sim snapshot               # the screen as an accessibility tree, refs like @e12
mac-sim ad press @e12          # tap (any agent-device command)
mac-sim shot /tmp/a.png        # a lossless screenshot to look at
mac-sim record /tmp/a.mp4 10 & # record while driving the flow...
wait; sim-fps /tmp/a.mp4       # ...then: 60 fps in every stretch of motion? dropped frames?
mac-sim down                   # give it back

The simulators skill is the agent's rulebook. After every UI change it runs the app, screenshots and looks, records the whole flow, and checks with sim-fps that motion held 60 fps with no dropped frames. It re-checks on a Release build (MODE=release mac-sim run) before calling the work done. sim-fps exits non-zero when a stretch drops frames, so the check is a pass or a fail, not an impression.

Measure motion on a 1x simulator (the default). On a modest GPU, 3x simulators can't reach 60 fps in heavy scenes, and that's the machine, not the app. On an Intel Arrow Lake iGPU a 1x simulator reached 92 to 96 fps in a heavy Liquid Glass benchmark.

Several agents at once

mac-sim keys each simulator to a checkout's git root. Two agents in two worktrees get two simulators, and mac-sim status shows who holds what. The default pool has two slim simulators plus full, sharp and small. Simulators nobody has used for 20 minutes shut down on their own.

T3 Code's Device panel

T3 Code shows simulators and emulators in its Device panel, and its agents can call device_open, device_screenshot and device_list. iOS needs a Mac, which T3 reaches over SSH; macbox's VM is that Mac.

./macbox t3 register   # add the VM to T3's deviceHosts (settings backed up first)
                       # open T3's Device panel once: T3 installs its device hub on the Mac
./macbox t3 fix-hub    # rebuild the hub's native parts for the Intel VM
./macbox t3 status

T3's hub ships its native parts for Apple silicon only; fix-hub rebuilds them for x86-64 from the hub's own source, including a fix that makes the VM's software H.264 encoder deliver each frame at once. Run it again after T3 updates its hub. Then:

  • mac-sim t3 prints hostId=macbox deviceId=<udid>; the agent passes them to device_open, and the user watches every tap live.
  • On iOS the agent keeps driving with mac-sim ad …. Using the agent-device command device_open returns as well would start a second session on the same simulator, and the two refuse each other (DEVICE_IN_USE).
  • From a tap to the first new frame on the stream: a median of 66 ms inside the Mac.
  • Android emulators started with android-sim show up in the panel by themselves (hostId local, the serial from android-sim serial).

Letting an agent set up macbox itself

An agent can do the whole installation, including the steps inside macOS's GUI. It looks at the VM's screen with ./macbox screenshot and acts with click, type, key and wait. Point it at AGENTS.md: it lists the sequence and the ground rules, such as asking before changing the host and never handling the user's passwords or Apple Account.

Android and real phones

  • android-sim has the same shape for Android emulators on the host: up, run, snapshot, ad, shot, record, down. It needs the Android SDK; see docs/agents.md.
  • The phone-builds skill and phone-build make an .ipa, a TestFlight upload or an .apk: Expo's free EAS cloud builds first, then locally (iOS in the VM). Device signing needs Apple's paid Developer Program.
